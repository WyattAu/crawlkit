# Capacity Evidence Plan — 10k/100k Instrumented Crawls

**Status:** Draft — procedure agreed; instrument implementation and hardware
runs pending
**Date:** 2026-09-13
**Closes toward:** PRODUCT_STRATEGY §3 6.0.0 row 1 (AR1 — "distributed mode
stable; published capacity evidence"); ROADMAP Phase 4.2 ("capacity report
committed with raw artifacts") and Phase 4.3 acceptance
**Shares fixtures with:** ADR-016 §5.1 (Parquet compression/encoding defaults
are picked by measured size/speed on the same 100k-page corpus)

---

## 1. What "capacity evidence" means here

The 6.0.0 claim is not "distributed mode exists" — `--distributed-mode` and the
graduated queue (ADR-015) already exist. The claim is that mode is
**defensible**: published, reproducible numbers for memory, file descriptors,
and concurrency with the raw artifacts attached, so a customer can size a
deployment and a maintainer can detect regressions mechanically.

Three commitments make the evidence honest:

1. **Named thresholds before measurement** (below) — numbers are judged
   against targets, not narrated after the fact.
2. **Raw artifacts committed** — every published number traces to a machine
   written run record (JSON), not a hand-copied table.
3. **Deterministic workload** — the corpus is generated and served locally;
   third-party sites never appear in evidence runs (politeness, legality, and
   reproducibility all demand it).

## 2. Named thresholds (measured on the reference environment, §3)

| Metric | Target (10k pages) | Stretch (100k pages) | Measurement instrument |
|---|---|---|---|
| Throughput | ≥ 50 pages/s | ≥ 50 pages/s sustained | run record: pages / wall time |
| Peak RSS | < 500 MB | < 2 GB | `VmHWM` from `/proc/<pid>/status`, sampled per page batch |
| RSS growth slope | ≈ 0 after warm-up (≤ 10% drift between 10% and 90% of crawl) | same | linear fit over RSS samples |
| Open file descriptors | returns to baseline ± 10 after crawl end; never > 2 × concurrent-fetch bound | same | `ls /proc/<pid>/fd \| wc -l` sampled |
| Tokio tasks | bounded: returns to near-baseline after crawl end | same | `RuntimeMetrics` (tokio_unstable) or task-count probe |
| Storage write amplification | reported, not gated | reported | SQLite/PG page-store size vs. fetched bytes |
| Export (shared with ADR-016 §5.1) | Parquet/JSONL export of the 100k fixture completes < 120 s | — | warehouse export timer |

Throughput and RSS are ROADMAP's published targets. The fd and task rows are
the "bounds" the strategy names: a crawl that leaks either is not a stable
distributed mode, whatever its speed.

## 3. Reference environment

- **Reference hardware:** 8-core / 16 GB RAM / NVMe, Linux, pinned rustc
  (workspace `rust-version`) — this is ROADMAP's reference spec. Capacity
  numbers are published **from this class of machine only**.
- **CI runners are a regression gate, not a source of published numbers:**
  hosted runners (4 vCPU) are noisy and slower; CI runs the smoke class (§6)
  and compares against a CI-recorded baseline relatively, not absolutely.
- Every run record embeds `uname`, CPU model, RAM, rustc version, crate
  version, and the crawl configuration hash, so a number is never separated
  from the machine that produced it.

## 4. Workload definition

- **Corpus:** deterministic synthetic pages generated by a fixture generator
  (seeded; committed generator, not committed corpus for 100k). Pages vary
  body size (0.5–50 KB), include links (bounded out-degree), sprinkle the
  issue-triggering shapes the analyzers detect (missing alt, missing
  description, heading soup), and exercise the redirect/404 paths at fixed
  ratios. 10k and 100k variants differ only in page count.
- **Serving:** local static server on loopback (the engine's test-server
  pattern), no TLS termination in the measured path unless a TLS variant run
  is explicitly labeled.
- **Crawl config pinned in the run record:** politeness budget, concurrency,
  page cap, `--distributed-mode` on/off, storage backend (SQLite default;
  PostgreSQL variant run for the distributed posture), plugins disabled
  except where a labeled run measures their cost.

## 5. Procedure (per labeled run)

1. Snapshot environment (§3 fields) into the run record.
2. Start sampler (RSS every 250 ms, fd count every 5 s, task count every 5 s)
   → `samples.json`.
3. Run the crawl; engine writes its own stats (`CrawlStats`).
4. On completion, hold for 10 s and take the post-crawl fd/task reading —
   this is the leak check against §2.
5. Emit `run_record.json`: environment, config, thresholds, medians, p95,
   raw sample paths.
6. **3 runs per configuration; publish the median; commit all three raw
   records.** A spread > 15% between runs invalidates the set (environment
   noise) — rerun, don't narrate.
7. The capacity report renders the committed records into tables; it never
   introduces a number that is not in a committed record.

Artifacts live under `docs/capacity/<date>-<config>/` (run records, samples,
report) — the Phase 4.2 "raw artifacts committed" requirement.

## 6. Regression gate (CI smoke class) — **implemented**

- **Workload:** 1k-page loopback corpus (index + 1000 children, deterministic
  sizes, fixed-ratio issue shapes), SQLite in-memory, inline mode, zero
  request delay — measured ~13 s locally.
- **Implementation:** `crates/crawlkit-engine/tests/capacity_smoke.rs`
  (ignored test; run by the `capacity-smoke` CI job in `ci.yml`). Samples
  RSS/fd/task counts from `/proc` at 100 ms, writes a `run_record.json`
  (schema `crawlkit.capacity.run_record/v1`) with environment, config,
  results, and gate outcomes, and uploads it as a workflow artifact.
- **Absolute caps (always enforced):** page budget exact (1001), peak RSS
  < 500 MB, throughput ≥ 20 pages/s, fds return to baseline + 10 after a
  settle period.
- **Relative gate (auto-arming):** the CI job caches the first green run's
  record as the baseline; `CAPACITY_ENFORCE=1` is set only on a cache hit, so
  subsequent runs must land within 20% of the CI baseline on throughput and
  peak RSS. Baseline updates are explicit (bump the cache key) with the
  superseding run record committed under `docs/capacity/` — same drift-gate
  philosophy as the capabilities manifest and the schema contract.
- Absolute numbers from CI are never published; the gate is relative.

## 7. Instrument notes

- RSS/fd/threads come from `/proc` (no dependencies; the `profiling` feature's
  `dhat` stays available for heap profiles when a threshold is breached — the
  *diagnosis* tool, not the *evidence* source).
- Tokio task counts require `RuntimeMetrics` (tokio_unstable). If enabling
  the cfg for the probe proves intrusive, the fallback is a periodic
  `/proc/<pid>/task` count — a coarser bound, labeled as such in the record.
- The load generator and sampler live in `crates/crawlkit-engine/tests/`
  (fixture side), reusing the engine's test-server, so measured behavior is
  the real engine path, not a mock.

## 8. Sequencing and open items

3. 100k runs → ADR-016 §5.1 compression defaults picked from the same runs.
4. Distributed-posture variant (queue + Postgres + multiple workers) → the

numbers (CI cannot provide it); whether the report renders into
`docs/` or the release notes (default: both, release notes link out).

## 9. What this plan does not claim

- No network-egress-bound numbers: loopback serving inflates throughput vs.
  the real internet by design; the published number is an engine-capacity
  number, labeled as such.
- No rendering-path numbers until the render-budget work (F5) lands its own
  budgets; a Playwright-in-the-loop run would measure a different engine.
- No shared-hosting comparisons; crawlkit's numbers stand alone.
